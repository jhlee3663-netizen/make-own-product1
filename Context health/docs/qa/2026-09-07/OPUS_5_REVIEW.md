## B. 신규 추가 항목

### V-ANON-MIGRATE · 잠재 P1 · 익명 세션 데이터가 다른 사람의 소셜 계정으로 영구 이전될 수 있음
- **판단:** 신규(보고서에 항목 없음)
- **보고서와의 관계:** V-AUTH에 "익명 계정→기존 소셜 계정 이동 시 로그 보존과 충돌 확인"이라는 **한 줄**은 있다. 그러나 (a) 이를 구현한 `migrateAnonymousData` 함수는 보고서·두 인계 문서·`source-excerpts.md` 어디에도 이름조차 등장하지 않고, (b) 서술이 "같은 사용자의 로그 보존" 관점이며 **서로 다른 두 사람 사이의 소유권 이전**이라는 위협 모델이 없다. 같은 파일의 `socialAuth`·`deleteAccount`·`sentryWebhook`은 조사했으면서 이 경로만 비어 있다.
- **증거(CODE):** `functions/index.js:92–139`. `socialAuth`가 커스텀 토큰 발급 **전에** `migrateAnonymousData(req, uid)`를 호출(`173`). `LoginScreen.jsx:83–95` `exchangeSocialToken`은 `auth.currentUser?.isAnonymous`가 참이면 **그 브라우저에 남아 있는 익명 세션의 ID 토큰**을 Authorization 헤더로 붙인다.
- **기대 / 실제(추적 결과):** 서버는 `sourceUid = 토큰의 uid`, 조건은 ① 토큰이 익명 로그인일 것 ② `users/{sourceUid}` 존재 ③ `users/{targetUid}` 미존재. 조건 충족 시 **`logs`의 `uid`를 targetUid로 영구 재할당**하고 프로필·coachRooms를 복사한다. 요청자가 소스 세션의 유효 토큰을 실제로 보유해야 하므로 임의 uid 위조는 불가하지만, **"토큰 보유자 = 그 데이터를 만든 사람"이라는 전제가 공유 기기에서 깨진다.** 공유 PC/태블릿에서 A가 게스트로 사용 후 로그인하지 않고 떠나고(Firebase Auth 세션은 브라우저에 계속 잔류), 이후 B가 같은 브라우저에서 카카오/네이버로 **최초** 로그인하면 세 조건이 모두 성립해 A의 기록이 B의 계정으로 넘어간다.
- **왜 QA-02보다 무거운가:** QA-02는 클라이언트 캐시 읽기이고 정리/새로고침으로 해소된다. 이쪽은 **Firestore 문서 소유권의 영구 이전**이라 캐시 삭제로 되돌아가지 않으며, A는 자기 기록을 되찾을 수단이 없다. 보고서의 P0 정의("회복 불가 손실") 자체에는 부합하나 "광범위한"에는 미달하므로, **잠재 P1로 등록하고 아래 판정 절차 후 등급 확정**을 제안한다.
- **다만 즉시 P1로 확정하면 안 되는 이유(반증 조건):** 현재 클라이언트 소스 어디에도 `signInAnonymously` **호출부가 없다**(`src/` 전체에서 `isAnonymous` 검사 8곳만 존재). 커밋 `41c5d92` 시점에 카카오/네이버가 쓰던 익명 로그인은 이후 커스텀 토큰 방식으로 대체된 것으로 보인다. 따라서 이 경로는 **과거 버전이 만든 익명 세션이 남아 있는 기기에서만 도달 가능한 레거시 경로**일 수 있다. 서버 함수 `socialAuth`는 배포되어 있으므로 경로 자체는 살아 있다.
- **판정 절차:** ① 현재 앱에서 익명 세션이 생성되는 경로가 정말 없는지 확정(온보딩·게스트 진입·Google/Apple 링크 경로 포함). ② 없다면, 과거 버전 익명 세션이 남은 기기가 실제로 존재하는지(Auth 콘솔의 익명 사용자 수·마지막 로그인) 확인. ③ 익명 사용자가 0이 아니면 전용 테스트 계정 2개로 위 시나리오를 비운영 환경에서 재현. ④ 도달 불가로 확정되면 **결함이 아니라 죽은 코드**로 분류하고 제거 여부를 별도 판단. **어느 쪽이든 지금처럼 "미조사" 상태로 출시 판정에 넣으면 안 된다.**
- **미검증 범위:** 실행 재현 없음. Auth 콘솔의 익명 사용자 통계 미조회.

### 누락 여정 · 계정 연결(link) 경로
- **판단:** 신규(범위표·V-AUTH에 구체 항목 없음)

- **왜 중요한가:** 연결 실패(`credential-already-in-use`, `provider-already-linked`, redirect 복귀 실패)는 인증·격리 결함의 고전적 발생 지점이고, 실패 시 사용자가 어느 uid로 귀결되는지가 곧 **어느 계정의 데이터를 보게 되는지**를 결정한다. 보고서 범위표의 "최초 접근·로그인" 행은 IdP 설정 조회와 Apple URI 요청만 수행했다고 적혀 있어 이 분기가 통째로 빠져 있다.
- **판정 절차:** 익명 세션 유무 × Google/Apple × popup/redirect × 이미 연결된 자격증명의 조합으로 종료 uid를 각각 기록. QA-09(Apple IdP 미설정)와 함께 검증할 것 — Apple은 로그인만이 아니라 이 연결 경로도 동시에 실패한다.

- **QA-17 / Rules 평가:** `evidence/rules-tests.json`을 직접 재확인했다. 10건 모두 `state: SUCCESS`이며 이는 "기대와 실제가 일치"라는 뜻이다. 마지막 2건은 기대값이 ALLOW인 **취약 조건 재현**이 맞고, 보고서가 이를 "보안 10/10 PASS로 읽지 말 것"이라고 명시한 것은 정확하다. 과대 해석 방지 서술을 그대로 유지할 것.
